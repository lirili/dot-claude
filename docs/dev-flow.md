# 開発フロー

## 要件

### 希望と課題

- 要件定義→設計→設計レビュー→実装→実装レビュー→最終手動テストの流れと、工程ごとの具体的な確認観点を残す。手動テスト前に必要な自動検証を済ませる。
- 要件定義・設計・テストにはユーザーが関与し、実装とコードレビューは可能な限りAIが完結する。
- 要件・設計で実装詳細まで決め、文書量が増えて誤りを見逃し、そのまま実装が進む問題を防ぐ。文書レビュー自体も重くしない。
- ユーザーの人力開発では、実現方法が見えない場合、方向性を置いてコードを試しながら設計を具体化している。後から設計を正確に整理し直す負担が大きく、コードだけが残りがちだが、複雑な実装でも設計文書を残したい。
- 分割の意味が乏しいクラスやメソッドの増加と、不具合検出の価値に乏しく変更のたびに保守が必要になるテストを抑える。
- 高難度かつ大規模で、多数のダイアログを含む1機能では、他の作業者へ要件を伝える難しさから一人で直接実装し、文書が残らないことがあった。この規模でも進められるフローを検討する。
- テスト未導入プロジェクトへ明示依頼なくテストコードを新規追加しない方針は維持する。
- 単位の文書は、今回限りの実装のための資料ではなく、恒久的な開発者向けの文書として整備する。改修では新しい文書を起こさず既存の文書を修正し、その差分を実装する。
- 文書など開発以外の成果物の単位にも、工程の骨格を適用できるようにする。開発に固有の確認観点・作成時の方針・検証手段・単位の例と配置は分野ごとに分け、分野を後から追加できる構成にする。文書作成の分野は、経験を積んでから追加する。
- 要件に挙げていない例外的な条件への対応を、実装者が独自に広げない。
- 改修の承認は、概要と承認の対象の項目と実際の変更差分で判断でき、管理の情報を読まなくてよい形にする。
- 親セッションは要件定義と進行の管理に留め、設計・実装・テストは工程ごとのセッションで、新しい文脈とモデルで進められるようにする。

### 本文書の書き方

- 工程の説明は、プロジェクトに慣れていない開発者にも、何を見て、何を行い、何を確認すればよいか分かる文にする。判断に必要な手掛かりを具体的に示す。
- 本文書にも「成果物の配置」の記述の範囲、更新の仕方、未確定の扱いを適用する。

## 役割

- ユーザー: 要件・設計の判断と承認、受け入れを行う。
- メインエージェント: 業務仕様の解釈、設計判断、実装、統合、最終検証を担う。単に「AI」と書く場合と、設計工程の「設計者」、実装工程の「実装者」はメインエージェントを指す。`~/.claude/CLAUDE.md` の条件で実装を委譲した場合も、確認と統合はメインエージェントが行う。
- レビュワー: 設計者・実装者とは別のエージェント。要件・設計・制約と、設計案または実際の差分を渡され、独立に確認する。
- サブエージェント: 調査・レビューなどの委譲先。利用条件は `~/.claude/CLAUDE.md` のサブエージェントの利用方針に従う。
- セッション: 要件定義と進行の管理、設計、実装、テストは別のセッションで行い、メインエージェントのモデルとエフォートはユーザーが工程ごとに選ぶ（アプリで親が子セッションを起こす場合は、ユーザーの指定で起こす）。既定値は、親・設計・テストのセッションが最上位の段、実装のセッションが中位の段、エフォートはいずれも xhigh とし、目安として使う。セッション間の引き継ぎは単位の文書だけで行い、引き継ぎのための別の文書を公開リポジトリに置かない。分野の skill は「分野」に従って読む。承認済みの設計の変更は設計工程の「承認後の変更」に従い、必要が出たセッションで変更案を示して再承認を得る。その設計レビューでは、要件定義の文面が残っていない範囲の扱いに従う。要件の補足・変更も、必要が出たセッションでユーザーの確認を得て要件の節（改修では「進行中の変更」の承認の対象）に反映するが、目的・対象範囲・完了条件を変える場合は親セッションへ戻す。reviewer・researcher への委譲はどのセッションからも行え、各セッションは自分の工程の調査・レビューを委譲する。
  - 親セッション: 依頼を受け、文書を持つ単位の要件定義を階層にかかわらず行い、ユーザーの承認を得る。上位の実装から下位の単位を始めるときも、下位の要件定義は親が行う。設計・実装・テストのセッションを順に起こし、その結果を単位の文書で受け取る。加える改修案の受付、改修の中止・縮小の承認、受け入れ後の「進行中の変更」の節の削除を行う。デスクトップアプリで親子の仕組みが使える場合は親が子セッションを起こして報告を受け取り、使えない場合と CLI ではユーザーがセッションを起こし、親は単位の文書で進行を把握する。
  - 設計セッション: 文書を持つ単位の設計・設計レビューを階層にかかわらず行い、ユーザーの承認を得る。要件定義のやり取りの文面を引き継ぐため、親の会話を引き継ぐ fork で起こす（CLI では `claude --resume <親のセッション> --fork-session` または `/branch`）。親の文脈の分だけ初期の文脈が大きくなる欠点は、親を要件定義と管理に留めて小さく保つことで受け入れる。引き継げない場合は、「設計レビューの進め方」の 1 の文面が残っていない範囲の扱いに従う。
  - 実装セッション: 実装と、それに伴う実装中の設計の具体化・試行、実装レビュー、下位の成果を組み合わせる上位の実装レビューを行う。実装中に確認した入力・操作と結果、確認できなかったことと理由は、単位の文書のテストの節に確認項目として書き、テストセッションに引き継ぐ（テスト・最終確認工程「残すもの」）。
  - テストセッション: テスト・最終確認工程、手動テストの引き渡し、受け入れの受け取り、下位の成果を組み合わせる上位のテストを行う。実装後の設計整理は単位の文書で引き継ぐ。問題が見つかれば、原因と再現条件を単位の文書のテストの節に記録し、修正は原因のある工程のセッション（親が起こすか再開する。親子の仕組みが使えない場合と CLI ではユーザーが起こす）で行い、修正後にテストセッションで再テストする。
  - 改修に当たらない変更の進め方: 要件定義・設計を経ない変更は、1 つのセッションで実装からテストまで行ってよい。
  - 再開と並行: 途中で止まったセッションは単位の文書から再開し、実装工程「要件・設計の読み方」の読み直しに従う。一つの単位で並行して進める子セッションは 1 つとする。
- レビュワーのモデル: レビューは、レビュー対象を作ったエージェントと同じモデルで、作った側以上のエフォートで行う。委譲には、呼び出したセッションのモデルを継承しエフォートを固定したレビュー用のエージェント定義を使い、新しいコンテキストで起動する。分野の単位では、その分野の skill を preload したレビュー用のエージェント定義を使う。分野の skill がない単位と、レビュー用の定義がない分野では汎用の定義を使い、後者では分野の skill を Skill ツールで読むよう依頼に書く（「分野」）。エフォートの値はエージェント定義（`~/.claude/agents/`）で定める。既定のサブエージェントのモデルを設定する項目（`CLAUDE_CODE_SUBAGENT_MODEL`）は使わない。

## フローの適用単位

- 基本: 目的と完了条件を説明できるまとまりに、要件定義→設計→設計レビュー→実装→実装レビュー→テストを入れ子に適用する。単位の例は分野の「単位と配置」に挙げる。各階層の要件定義・設計・設計レビュー・実装レビュー・テストは、その階層の対象全体について行う。固定の階層数を前提にせず、実際の責務・包含関係・利用関係に合わせて単位を選ぶ。
- 文書と工程の対応: 上位の文書では「実装」から、その実現を担う下位の文書を参照する（例は分野の「単位と配置」）。下位の文書には、その対象の要件定義→設計→設計レビュー→実装→実装レビュー→テストの流れをまとめる。この下位の開発フロー全体が、上位の「実装」に当たる。下位の「実装」も必要に応じて、さらに下位の文書と開発フローへ展開する。
- 上位から下位へ: 上位で目的・全体像・責務の境界・共有データや契約・制約・完了条件を押さえ、下位では担当範囲に必要な内容を具体化する。上位のすべての詳細を決め終えてから下位へ進む必要はなく、未確定の前提に依存する範囲を明確にして進める。
- 下位から上位へ: 上位で今回扱う範囲に必要な下位の開発フローがテストまで完了したら、その成果を組み合わせて上位の実装レビュー・テストを行う。上位の要件・設計と完了条件を満たせば、そこまでの成果がさらに上位の「実装」の成果となり、その上位の実装レビュー・テストへ進む。未対応・未確認の範囲も引き継ぎ、部分的な完了を対象全体の完了として扱わない。
- 見直し: 下位の調査・設計レビュー・実装・実装レビュー・テストで、合意した要件・設計を変える必要が判明した場合は、影響範囲を確認し、その要件・設計を管理する階層の判断へ戻る。影響する他の単位と共通ルールも見直す。
- 上位の不足: 下位の作業で、複数の単位に共通する構成・データ・ルールの判断が必要だと分かった場合は、それを管理する上位の文書を作るか既存の上位文書に補い、ユーザーの確認を得てから下位に戻る。上位全体を決め直すのではなく、今回の判断に必要な範囲に限る。
- 共通事項と個別事項: 共通の要件・設計・判断基準は上位を参照し、下位には固有の内容と差分を記述する。同じ工程を適用しても、各階層の文書と承認は、その階層で決めた固有の内容と差分に限り、上位で承認済みの内容を再確認しない。ユーザーへの確認は、各階層の固有の判断、業務上の成果を確認できる単位での受け入れ、承認済みの設計の変更に必要な範囲で行う。

## 分野

- 分野: 成果物の形によって確認観点と検証手段が変わるまとまりを分野と呼ぶ。分野に固有の内容は、分野ごとの文書（`docs/dev-flow-<分野>.md`）に、単位と配置、調査の対象、要件の確認事項、設計の確認対象、作成時の方針、レビューの観点、検証手段、版の識別の節で書く。各工程の記述は、分野固有の内容を「分野の『節の名前』」の形で参照する。
- 分野の決め方: 単位ごとに決める。単位の成果物に、実行・ビルド・テストで確かめるコード・スクリプト・設定が含まれるなら開発分野とする。ここでの「確かめる」は、成果物の正しさを実行・ビルド・自動テストの結果で判定することを指す。Claude Code の設定・skill・エージェント定義のように、読まれて指示として働き、読んで照合して正しさを判定する成果物は、開発分野に含めない。開発分野でない単位は分野の skill を読まず、骨格（本文書の各工程）だけで進める。
- 分野の skill: 分野の文書は 1 本の skill に反映し（「skillへの反映」）、どのセッションでも入口の次に読む。
- 工程の名前: 「実装」は、分野にかかわらず単位の成果物を作る工程を指す。工程の名前は分野で変えない。
- 分野の一覧:

| 分野 | 文書 | skill | レビュー用エージェント定義 |
| --- | --- | --- | --- |
| 開発 | `docs/dev-flow-code.md` | dev-flow-code | reviewer-code |

- 分野の skill がない場合: 各工程の記述が分野の節を参照する箇所では、AI が対象の成果物に合わせて該当する内容をその場で挙げる。要件定義・設計では、挙げた内容をユーザーの確認対象に含める。実装・レビュー・テストでは、挙げた内容を自己レビュー・検証の結果とともに示す。レビューの委譲には汎用のエージェント定義（reviewer）を使い、挙げた内容を渡す。
- 分野の追加: 分野の文書と skill を同じ節構成で作り、分野の一覧に加える。レビュー用のエージェント定義を作る場合は、既存の定義と同じ形で追加する。

## 成果物の配置

- 単位と文書: 単位ごとに1文書を、対象プロジェクトの `docs/` に置き、階層に合わせて配置する。プロジェクトのフォルダがない成果物では、成果物と同じ場所に置く。配置の例は分野の「単位と配置」に挙げる。文書を持つ単位は、独立した要件・設計・テストを持つ単位に限る。文書を持たない単位は、それを含む文書の設計と実装の節の中で扱い、工程は同じ順で適用するが文書一式は作らない。
- 文書の位置づけ: 単位の文書は、開発者がその単位の現在の仕様を知るための文書として、単位がある間は維持する。依頼や変更ごとに要件・設計の文書を作らない。
- 文書の構成: 節は要件、設計、実装、レビュー、テストとする。「進行中の変更」の節は、書く内容がある間だけ要件の節の前に置く。実装の節には下位の文書への参照を置き、下位を持たない場合は、その単位を実現する成果物の場所や主要な参照先を示す。レビューの節は、未解決の指摘がある間だけ置く。
- 記述の範囲: 文書は現在の要件・設計・未実施事項だけを持つ。レビューの指摘やテストの結果は、未解決・未確認のものだけを該当する節に残し、解消したら削除する。経緯や作業ログは残さない。
- 重複を避ける書き方: 同じ説明を複数の箇所に繰り返さない。複数の箇所で使う用語は一度だけ定義して参照し、複数の条件が組み合わさる判定は表にまとめる。
- 根拠の出典: 判断に使った資料や成果物の参照先は、調査手順の「報告の形」に従って残す。承認するユーザー以外の人に確認した業務ルール・外部仕様のうち、成果物や他の文書から確かめ直せないものには、確認先を部署や役割で該当箇所に短く添え、個人名や確認までの経緯は書かない。
- 更新の仕方: 未確定の事項が確定したら、決定内容を本文の該当箇所に反映し、未確定としての記載を削除する。「決定済み」「反映済み」などの注記や決定までの経緯を追記せず、未確定の事項がなくなった欄や見出しも削除する。
- 未確定の扱い: 未確定の節や項目には「案（未確認）」のように印を付け、確定した内容と区別する。追記と見直しを重ねて項目内の記述を完成させ、ユーザーが確認して合意した時点で印を外す。印の付いた内容を、承認済みの要件・設計として扱わない。
- 分割の基準: 文書を分けるかどうかはサイズではなく、独立した要件・設計・テストを持つ単位かどうかで決める。
- 全体の目的と計画: プロジェクト全体の目的・範囲・制約・完了条件は最上位の文書の要件の節で、単位の分割は実装の節で、進める順序は「進行中の変更」の節の管理で扱う。憲章や計画の別の様式は、必要になった時点で検討する。

### 既存の単位を改修する場合

- 対象: 一度受け入れた単位、または文書がまだない既存の単位（文書を持つ単位に当たるもの）への変更のうち、要件、または設計工程の「ユーザーの確認対象」に当たる判断を、新たに決めるか変えるもの。以下、これを改修と呼ぶ。動作を変えない整理でも、確認対象の判断を変える場合は改修に当たる。
- 改修に当たらない変更: 対象の判断を変えない変更（文書どおりでない動作の修正、文書の粒度より細かい変更、判断を変えない整理など）では、「進行中の変更」の節を作らず、本文の詳細を設計工程の「実装中の文書更新」に従って更新する。文書がまだない単位や未記載の範囲では、文書を作らず補わず、確認項目と結果はユーザーへの報告で示す。
- 文書の扱い: 新しい文書を作るのは、「分割の基準」を満たす新しい単位が生じる場合と、文書がまだない既存の単位を改修する場合に限る。既存の上位に新しい単位を加える場合、新しい単位は通常の流れで文書を作り、上位の文書に参照を加える。上位の文書に書いた要件や、責務の境界・共有データ・契約を変える場合は、上位も改修として扱う。単位を廃止・統合する場合は、統合先と上位の文書を変更案として書き換え、廃止する単位の文書は受け入れ後に削除する。
- 変更案の書き方: 本文は変更後の内容に書き換え、変更前との対比や変更の経緯を書かない。ユーザーの確認前は、書き換えた項目に「未確定の扱い」の印を付け、合意した時点で印を外す。変更後も単位の動作として残る内容（旧形式のデータの読み込みなど）は、本文に書く。変更する記述に基づく実装が進行中の場合（初回の開発の途中、承認済みの変更案を改修の途中で変える場合）は、設計工程の「承認後の変更」「実装中の文書更新」に従い、再承認後に本文を更新する。改修の途中では、その変更案（変更点の更新と、判断に必要な詳細）を「進行中の変更」の節に印を付けて書く。判断に必要な詳細は承認の対象の該当する項目（なければ判断事項）に、変更点の更新は管理に書く。
- 「進行中の変更」の節: 未実施事項として、次のうち該当する内容を短く書く。この節がある間は、未了の作業（実装、受け入れ）があることを示す。新しい単位の開発でも、該当する内容（既存動作やデータへの影響、移行、実装の順序）がある場合は、この節に書く。節は「承認の対象」と「管理」の二つの小見出しに分け、ユーザーは承認の対象と印の付いた本文を読んで判断し、管理は AI とレビュワーが使う。管理の項目の印は、対応する変更案が未承認であることを AI とレビュワーに示し、ユーザーの確認の対象ではない。書く内容がない小見出しは省く。
  - 承認の対象:
    - 概要（改修の場合）: 何をどう変え、なぜ変え、ユーザーが何を判断するか（判断事項への参照でよい）を、5 文以内で書く。変更の目的を含める。
    - 今回の変更に固有の利用場面・期待する動作・対象範囲・制約・完了条件。
    - 既存動作やデータへの影響。
    - 移行の手順と移行時の確認。受け入れまでに行うものに限り、受け入れ後に行う移行はこの開発フローの外で管理する。
    - 受け入れの時期。進行中の改修に改修案を加えて一度に受け入れる場合に書く。
    - 判断事項。ユーザーの判断を要する事項（承認済みの事項を変える点、要件にない追加、重要なトレードオフの選択、未確定の事項）を、本文の該当する節の名前とともにすべて挙げる。本文の該当箇所に印を付けて書けない事項（再承認の判断に必要な理由・影響範囲・トレードオフを含む）は、ここに案を書く。設計者は承認を求める前に、判断を要する変更がすべて挙がっているか確かめる。確定したら「更新の仕方」に従って、決定内容を該当する項目または本文に反映して削除する。
  - 管理:
    - 変更点: 変更する節・項目と、何をどう変えるかの要約。追加と削除を含む。AI が実装する範囲の把握と差分の網羅の確認に、レビュワーが差分の網羅の確認に使う。
    - 実装の順序（下位の単位を進める順序を含む）。分けて進める場合に書き、承認の対象にせず印も付けない。
    - 現状を書き起こした節・項目（書き起こした場合）。
    - 改修を始める前の版（コミットIDなどの識別子）。
- ユーザーの確認: 節の承認の対象の確認前の内容にも印を付け、本文の変更案とあわせてユーザーの確認を得る。ユーザーの確認は、この節の承認の対象と印の付いた本文の項目に限り、管理の項目と変更しない記述を再確認しない。
- 設計整理と照合の範囲: 一度受け入れた単位への変更では、改修に当たらない変更も含め、実装後の設計整理とテストの完了条件の照合を、変更した箇所とその影響範囲について行う。
- 複数の改修: 「進行中の変更」の節がある単位への別の改修は、進行中の改修の受け入れ後に始めるか、進行中の改修に加える。加える改修案は、要件の承認までは節の承認の対象の末尾に一つの項目として印を付けて書き、要件の承認後に承認の対象の各項目に統合する。その設計の変更点は、管理の変更点に印を付けて加える。加える改修案の受付と要件定義は親セッションで行う。
- 複数の単位にまたがる改修: 改修として扱う単位（その単位の文書で、対象の判断を新たに決めるか変える単位。成果物を変えない単位と、その改修で新しく作る単位を含む。改修に当たらない変更だけが入る単位と、影響の扱いをほかの単位の文書で決めるだけの単位は含まない）が複数ある場合は、共通の内容（概要、制約、完了条件、単位をまたぐ実装の順序、改修を始める前の版など）を一つの文書の「進行中の変更」の節に、承認の対象と管理の区分に従って書き、その承認の対象の冒頭に、改修として扱う単位の文書を挙げる。続けて概要を書く。他の文書の節は、承認の対象の冒頭でその節を参照し、その単位に固有の内容を書く。概要は共通の内容として置き場の文書にだけ書く。置き場の理由を書く必要はない。共通の内容を置く文書は、置き場の1〜3の順で決める。
  - 置き場の1（上位の単位）: 改修として扱う単位の一つが、改修として扱うほかのすべての単位の上位である場合は、その単位の文書に置く。
  - 置き場の2（中心の単位）: 1に当たらない場合は、改修として扱う単位のうち、その上位に改修として扱う単位がないものを候補とする。ほかの候補がいずれも、一つの候補（その下位を含む）の要件・設計の変更を反映するか、その影響を受けるために改修の対象になっている場合は、その候補を中心の単位、ほかの候補を関連する単位と呼び、中心の単位の文書に置く。ほかの候補の変更点や本文が、その候補の要件・設計の項目を参照していることを手掛かりにする。関連する単位が、反映に伴う固有の判断や、改修に加えた別の変更を持っていても、中心の単位は変わらない。
  - 置き場の3（中心の単位が一つに決まらない場合）: 候補に共通する最も近い上位の文書に置き、共通する上位の文書がなければ、候補の一つの文書に置く。上位の文書に置いた節は共通の内容の置き場であり、上位を改修として扱わない。
  - 改修として扱わない上位の文書: 共通の内容の置き場とする場合を除き、「進行中の変更」の節も、進行中の改修があることを示す記述も置かない。その文書（今回作る場合を含む）に、判断を新たに決めず変えもしない差分（単位への参照の追加、「上位の不足」で書き起こした現状）が生じる場合は、共通の内容を置いた節の変更点または現状を書き起こした節・項目に挙げる。
  - 関連する単位の扱い: 中心の単位の節の完了条件に、冒頭に挙げた関連する単位のテストの節の確認（ユーザーの手動確認を含む）を含める。確認項目は各単位のテストの節に置き、完了条件に写さない。受け入れは、テスト・最終確認工程の「関連する単位の受け入れ」に従う。中心の単位の文書の実装の節には、関連する単位への参照を置かない。
  - 節を削除する時期: 関連する単位の節は、中心の単位の節とあわせて削除する。共通の内容を置いた節は、それを参照する節が残る間は削除せず、置き場の3で改修として扱わない上位の文書に置いた節は、参照する節をすべて削除した時に削除する。ほかは「節の削除」に従う。
- 節の削除: 受け入れが済んだら節を削除する。削除と、改修の中止・縮小の承認は親セッションで行い、中止・縮小で戻すときは、変更点の項目は親が、成果物は実装セッションが戻す。受け入れを上位に含める下位の単位では、その改修を含む上位の受け入れ後に削除し、それまでは節が受け入れ待ちの記録になる。節を含む版をコミットしてから削除し、変更の経緯を履歴でたどれるようにする。改修を中止または縮小する場合は、「承認後の変更」に従ってユーザーの承認を得てから、改修を始める前の版を元に、取りやめる変更点の項目と成果物を戻し、中止の場合は節も削除する。確認済みの書き起こした現状は残す。
- 文書がまだない既存の単位: テンプレートから文書を作り、今回の変更の判断に必要な範囲の現状を、既存の成果物で確かめて書く。成果物から分からない目的や判断理由は、ユーザーに確認するか未記載とする。書き起こした現状にも印を付け、維持する仕様としてユーザーの確認を得る。意図と異なる動作が分かった場合は、変更点に加えるか、設計工程の「既知の問題」として扱う。書いていない範囲は「上記以外は未記載」のように該当する節に示し、そこに改修が入る時点で補う。文書はあるが未記載の範囲を持つ単位で、その範囲を補う場合も同じ扱いとする。

## 要件定義工程

- 目的: 何を実現し、何ができれば完了かをユーザーとAIで共有する。
- AIの担当: 会話、既存資料、関連する成果物から案を作る。調べられる事実は調べ、確認済み事項と推定を区別し、ユーザー判断が必要な点を絞る。
- 抜けの確認: 案をユーザーに示す前に、依頼の各事項が、対象外とするものを含めて案に入っているかと、分野の「要件の確認事項」の各事項に当たるものが今回の対象（改修では変更点）にあるかを、依頼と既存の文書・成果物に照らして確かめる。当たるもののうち目的・範囲・完了条件を左右するものは、確認済みの内容を案に書き、推定とユーザーの判断が要るものは未確定事項として示す。違いや条件を設けないと決める場合も案に書く。設計で決める詳細は設計工程で扱う。当たるものがない事項は文書に書かず、案を示すときにユーザーへ短く伝え、変わらなければ繰り返さない。
- ユーザーの確認対象: 目的・利用場面、期待する動作と完了条件、対象範囲・制約、重要な未確定事項。既に明確に伝えられた内容や確認済み事項は、変更がなければ再確認しない。
- 残すもの: 上記の判断内容を短くまとめた本文を基準にする。実装手順や成果物の中身は、指定された制約や外部との契約として必要な場合だけ要件に含める。
- 次へ進む条件: 設計の出発点となる目的・期待する動作・範囲・完了条件について重要な認識差が解消されている。設計や調査で詰める事項は未確定として残す。
- 後工程との関係: ユーザーが確認していない業務仕様をAI向けの詳細資料で追加・確定しない。
- 改修の場合: 単位の文書の要件の節を読み、成果物の配置の「既存の単位を改修する場合」に従って変更案を示す。要件の節には単位が満たす内容を書き、今回の変更に固有の内容は「進行中の変更」の節の承認の対象に書く。

## 設計工程

- 目的: 要件を満たす仕組みと、実装を任せるための重要な判断を共有する。
- AIの担当: 既存構造と影響範囲を調べ、重要な設計判断の選択肢とトレードオフを整理する。事実確認で解決する事項は調査する。
- ユーザーの確認対象: 全体構成と責務の分担、分野の「設計の確認対象」に挙げる確認対象、既存動作やデータへの影響、重要な選択肢のトレードオフ、テスト観点。
- 設計レビュー: 承認を求める前と、承認済みの設計の変更案を再承認に出す前に、レビュー工程の設計レビューを受ける。
- 承認後の変更: 承認済みの設計を変更する場合は、変更の大小や理由にかかわらず、必ずユーザーの明示的な再承認を得る。セカンドオピニオンによる改善案も含め、変更案・理由・影響範囲・トレードオフ・やり直す工程を短く示す。再承認までは変更案を未承認として扱い、その変更を実装へ反映せず、それに依存する下位工程も進めない。
- 改修の場合: 変更案は、「実装中の文書更新」の本文を更新する時期によらず、成果物の配置の「既存の単位を改修する場合」の「変更案の書き方」に従って本文に書く。設計レビューとユーザーの承認を得てから実装へ進む点は「承認後の変更」と同じとする。既存動作やデータへの影響と一度だけ行う移行は「進行中の変更」の節の承認の対象に、変更後も残る互換の動作は設計の節に書く。
- トレードオフ: 重要な設計判断では、現実的な選択肢ごとに利点・欠点・制約を比較し、今回の目的や条件に基づく推奨案と理由を示す。比較軸は作業量・保守性・性能・運用負担など判断に関係するものに絞り、形式的に案や説明を増やさない。
- 残すもの: 選んだ設計と採用理由・制約・受け入れる欠点を本文に置き、図や表は判断しやすくなる場合に使う。個々の実装手順は、重要な境界・外部との契約・要件上の制約を決めるために必要な範囲だけ具体化する。
- 既知の問題: 意図しない動作のうち、ユーザーが直さずに残すと判断したものは、設計の節に「状況・起きること・扱い」の表でまとめる。扱いには、許容する理由、回避方法、後で直す予定などを書く。ユーザーの判断をもって書き、設計の変更案としては扱わない。テストで見つけて残す場合は、確認項目の期待する結果に既知の問題への参照を書き、状態を空欄にする。選んだ設計に伴う欠点は、「残すもの」に従ってその設計判断の記述に添える。
- 実現方法が不確かな場合: 設計の方向性と未確認の技術的仮説を区別し、試作で確かめる事項・判断基準・試す範囲を短く示す。AIが承認済みの設計を変えない範囲で、小さく実装・検証する。未確認の仮説を後続実装の確定前提にしない。採用する試作には通常のレビューと検証を行う。
- 実装中の文書更新: 構成・データ・主要な処理や設計判断が具体化した段階で、承認済みの設計と矛盾しない内容を本文の該当箇所へ反映する。具体化した内容は、ユーザーが承認した判断（「ユーザーの確認対象」）の範囲内の詳細として印を付けずに書き、その後の変更は承認した判断を変えない限り再承認を要しない。承認済みの設計を変更する場合は、変更案を確定内容と分けて示し、再承認後に本文を更新する。採用理由と受け入れる欠点も短く記し、成果物の編集ごとの作業ログは追記しない。
- 実装後の設計整理: AIが最終の成果物を確認し、構成・責務・データ・主要な処理の全体像が分かる設計文書に整える。成果物の逐語的な説明は増やさず、必要な参照先を示す。成果物から分からない判断理由を推測で補わない。要件・実際の成果物・検証結果と照合し、不一致をそのまま仕様化せず解消するか未確認事項として示す。実装レビューへ進む前に行い、レビューやテストの修正で成果物が変わったら再度行う。テスト・最終確認工程の完了条件に含める。
- 次へ進む条件: 設計レビューを終え、進める範囲に必要な要件との対応、重要な設計判断とトレードオフ、影響範囲、確認する動作が共有され、ユーザーの承認を得ている。ユーザーが決める事項が未確定の場合は、その判断に依存する実装を確定しない。合意した範囲内で、承認済みの設計を変えない技術的な試行と局所的な実装判断はAIに任せ、見通しが得られた範囲から実装を進める。

## 実装工程

- 目的: 合意した要件・設計を満たす成果物を作り、レビューできる状態に整える。
- AIの担当: メインエージェントが全体の整合を保ちながら、動作や仮説を確認できる単位で実装・検証・修正を進める。実現方法が不確かな部分は、設計工程に定めた試行と見直しの方法を使う。
- 要件・設計の読み方: 実装者自身が、成果物を変える単位ごとに、その単位の成果物を作る前に次の範囲を最後まで読む。単位の文書（文書を持たない単位では、それを含む文書）の全体、上位の各階層の文書の「進行中の変更」（ある場合）・要件・設計の節、単位の文書が節・項目を示して参照する他の単位の文書の該当箇所。文書がまだない単位では、このうち文書があるものを読む。関係しそうな箇所だけを選んで読むこと、実装の途中で必要になった箇所をその都度読むこと、他のエージェントによる要約を読むことで、これに代えない。一度読んだ範囲は、「実装の進め方」の4の読み直しを除いて読み直さなくてよい。ただし、実装を別のセッションで再開するときと、会話の履歴が要約された後に実装を続けるときは、同じ範囲を読み直す。
- ユーザーに戻す条件: 調査や試行で解決できる事項はAIが確認する。承認済みの設計を変える必要がある場合は、設計工程の「承認後の変更」に従ってユーザーの再承認を得る。業務仕様や重要なトレードオフなど、合意した範囲を超える判断も、影響と推奨案を示して該当する判断へ戻る。
- 文書との同期: 設計工程の文書更新・実装後の設計整理に従い、現在の成果物と設計を揃える。説明がつかない不一致や未確認事項を隠さない。
- 改修の場合: 「進行中の変更」の節の管理の変更点と、そこに挙げた本文の項目から、今回実装する範囲を把握する。変更点に挙げていない動作は、文書に記述がないものも含めて、維持すべき既存動作として扱う。読む範囲は変更点に挙げた項目に絞らず、「要件・設計の読み方」に従う。
- 実装レビューへ進む条件: 対象範囲の実装、差分全体の自己レビュー、実行可能な検証と必要な修正を終え、実際の差分、要件・設計との対応、自己レビュー・検証の結果、未確認事項を確認できる状態にする。試作や一部分の動作成功だけで、対象全体が完成したと扱わない。

### 実装の進め方

1. 合意した要件・設計と、分野の「作成時の方針」に挙げる読む対象を読み、実現する動作と変更の影響を確認する。要件・設計は「要件・設計の読み方」に従って読む。維持すべき既存動作も踏まえ、確認する入力・操作、期待する結果、確認方法を考える。確認方法はテスト・最終確認工程に沿って決め、手動テストで確かめる項目と実行する既存の検証を分ける。
2. 設計で大きな変更をまとめて渡された場合は、実装者が変更の目的・差分・確認方法を把握できる単位に分け、依存関係を踏まえて実装順序を決める。分け方や順序は、実装で分かったことに応じて見直す。
3. 作る前に、流れを短く整理し、見通しを付ける。整理する内容と置き場は分野の「作成時の方針」に従う。
4. 整理した流れに沿って、動作を確認できるまとまりごとに実装・自己レビュー・検証を進める。まとまりに着手するときは、「要件・設計の読み方」の範囲を読んだ直後を除き、その範囲のうち、そのまとまりに関係する箇所を読み直し、最初に読んだときの記憶だけに頼らない。複雑な部分では、その内部でも流れと確認方法を具体化してから実装する。実装・自己レビュー・検証で分かったことを踏まえて、整理した流れや設計、確認方法を見直す。必要な修正を反映し、実装・検証を続ける。見直しで承認済みの設計を変える必要が分かった場合は、「ユーザーに戻す条件」に従う。
5. 変更単位ごとに、差分の自己レビューと必要な検証・修正を終えて、次の単位へ進む。版の区切りは分野の「版の識別」に従う。
6. レビュワーへ引き渡す前に、対象変更の差分全体と最終の成果物を自己レビューし、コミットをまたぐ不整合や対応漏れを確認する。各部分を組み合わせた動作も検証し、必要な修正・再確認を終える。自己レビューと検証で確認した範囲と結果、確認できなかったことと理由を短く示す。

### 自己レビュー

- 要件・設計と、実際の差分・周辺の成果物を照合し、対応漏れや処理の不整合がないか確認する。
- 本工程の進め方・分野の「作成時の方針」・プロジェクトの規約を読み返す。今回の変更に適用するルールが守られているか、実際の作業と成果物に照らして確認する。
- 実装ルールへの適合は実装者が確認する。見つかった問題は実装者が修正し、修正箇所と影響先を再確認する。

### 検証

1. 合意した要件・設計と維持すべき既存動作から、対象範囲の入力・操作と期待する結果を確認する。既に確かめた動作と、追加で確認が必要な動作を整理する。
2. 分野の「検証手段」に従い、実行できる確認を行う。
3. 実行結果を読み、期待する動作を確かめられたか確認する。
4. 問題があれば修正し、直した箇所と影響を受ける箇所をもう一度確認する。確認が済んだ後は、新たな変更や懸念がなければ繰り返さない。

## レビュー工程

- 目的: 成果物を作ったエージェントとは別の視点で、その階層の要件・設計に照らして確認する。設計レビューでは、要件を依頼・上位の文書・既存の成果物に照らして、抜け・複数の読み方ができる記述・矛盾がないかを確認し、設計案が要件を過不足なく満たし、上位の設計・既存の構成と整合するかを確認する。実装レビューでは、成果物が要件・設計どおりに正しく動作し、理解・変更・検証しやすい構成になっているかを確認する。
- 時期: 設計レビューは、設計案をユーザーの承認に出す前と、承認済みの設計の変更案を再承認に出す前に行う。実装レビューは、実装の「実装レビューへ進む条件」を満たしたときに行う。
- AIの担当: 設計者・実装者とは別のエージェントがレビューを行う。メインエージェントは指摘の根拠を確認し、必要な修正と検証を行う。
- 自己レビューとの分担: 実装者が実装ルールへの適合を確認・修正したうえで、レビュワーも成果物を独立に確認する。要件の充足、処理やデータのつながり、既存動作への影響に加え、保守性と実装方法の妥当性を確認する。
- 候補の扱い: レビュワーは、問題が起きる条件を言える候補をすべて挙げ、重大度や確信度で自分では絞らない。採否と重大度は作った側が根拠を確かめて決める。レビュワーへの依頼に、「重大なものだけ」「保守的に」のように候補を減らす指示を書かない。
- 指摘の書き方: 対象箇所（コードはファイルと行、文書は節と該当文）、問題が起きる入力・状態、期待と異なる結果を短く示し、修正が必要な問題と任意の改善提案を区別する。名前や見た目からの推測を根拠にせず、コードや文書の該当箇所を示す。
- 指摘への対応: 作った側は指摘ごとに根拠を確かめ、問題があると確かめた「問題あり」、確かめる手段はあるが未確認の「未確認」、コードや文書で反証できる「問題なし」に分ける。問題なしは反証を示せる場合に限る。未確認は捨てず、設計レビューではユーザーの確認対象へ、実装レビューではテストの節の確認項目へ移す。採用しない指摘は理由を短く示す。
- レビューの終了: レビュワーは、最初の指摘を見つけた後も対象全体を最後まで読み、該当する指摘をすべて挙げてから終える。該当が無ければ「指摘なし」と報告し、数を合わせるための指摘は作らない。
- 委譲: レビュワーは新しいコンテキストで起動し、要件・設計・制約と成果物（設計案または差分）を先に、確認の依頼と指摘の条件を後に置いて渡す。設計レビューでは、「設計レビューの進め方」の1のやり取りの文面も、要約せずに渡す。長い資料では、判断の前に該当箇所を引用させる。
- 改修のレビュー: 設計レビューでも実装レビューでも単位の文書の全体を読み、「進行中の変更」の節の管理の変更点を起点に確認する。どちらも、改修を始める前の版からの文書の差分が、変更点または書き起こした節・項目にすべて挙がっているか確認する。この網羅の確認はユーザーの確認の対象ではなく、作った側とレビュワーが担う。判断を要する変更（承認済みの事項を変える点、要件にない追加、重要なトレードオフの選択）が、承認の対象の判断事項にすべて挙がっているか確認する。実装レビューでは、承認後の「実装中の文書更新」による具体化を除く。設計レビューでは、変更案が変更しない記述と矛盾しないか、変更に合わせて直すべき記述が残っていないかを確認し、書き起こした現状の記述を成果物と照合する。実装レビューでは、変更前の仕様が必要な箇所で改修を始める前の版の記述を参照し、改修に当たらない変更として進めた場合は、その判定が妥当か確認する。
- 複数の単位にまたがる改修のレビュー: 対象の単位の文書に加えて、共通の内容を置いた節と、対象の文書が参照する他の単位の文書の項目を読み、委譲するときはこれらも渡す。共通の内容を置いた節か、それを参照する節を、書くか変える設計案の設計レビュー（承認に出す前と、再承認に出す前）では、共通の内容を置いた節（上位を改修として扱わない場合を含む）と、その時点で書かれている参照する各文書の節をあわせて読み、共通の内容の置き場が成果物の配置の「複数の単位にまたがる改修」に合うか、共通の内容と各単位に固有の内容に食い違いや抜けがないかを確認する。共通の内容を置いた節に挙げた、改修として扱わない上位の文書の差分も、このレビューの対象に含める。中心の単位の実装レビューでは、関連する単位を「実装レビューの進め方」の3の下位と同じ扱いとする。
- 次へ進む条件: 設計レビューでは、必要な修正が終わり、残る事項がユーザーの確認対象として整理されている。実装レビューでは、必要な修正と再確認が終わり、テストへ進むことを妨げる未解決の問題がない。未確認事項は理由と影響を示し、最終テストで確認する内容と、先に判断・解消すべき事項を明確にする。

### 設計レビューの進め方

1. 対象の要件、上位の要件・設計と共通ルール、設計案、調査結果と未確認事項を読む。今回の対象についてのユーザーの依頼と、要件に関するAIの提示とユーザーの回答は、設計者の要約ではなく、やり取りの文面を読む。文面が残っていない範囲は設計者がその旨を伝え、レビュワーは依頼と照合できなかった範囲を報告に示し、設計者はその範囲をユーザーの確認対象に加える。設計セッションを親の会話を引き継いで起こした場合は、親セッションでの要件定義のやり取りが文面に当たる。気になる点は元の文書や既存の成果物をたどって確かめる。
2. 要件を、やり取りの文面、上位の文書、既存の成果物と照合する。依頼にあって要件にない事項、やり取り・上位の文書・既存の文書と成果物のどこにも根拠がないのに確定した内容として要件にある事項、複数の読み方ができる記述、確かめる方法が決まらない完了条件、要件同士や上位の要件との矛盾を挙げる。要件定義工程の「抜けの確認」の事項は、対象に当たるものがあるのに、期待する結果が要件・設計案・上位の文書のどれからも決まらない入力・操作・状態を示して指摘する。未確定として残した事項と、下位の単位で決めると書いた事項は、記述があるものとして扱う。改修では変更点に、承認済みの設計の変更案のレビューでは変更案に、関係する範囲を対象にする。
3. 要件の各項目が設計のどこで実現されるかを確認し、満たされていない要件と、要件にない機能・制約の追加がないか確認する。
4. 構成と責務と、分野の「設計の確認対象」に挙げる確認対象が互いに矛盾せず、上位の設計・既存の構成と整合するか確認する。既存動作やデータへの影響に見落としがないか確認する。分野固有の整合は、分野の「設計の確認対象」の設計レビューでの確認に従う。
5. 重要な設計判断について、比較した選択肢と採用理由が要件・制約に照らして成立するか、未確認の技術的仮説を確定した前提として扱っていないか確認する。テスト観点が要件と設計の重要な動作・例外を覆っているか確認する。
6. 設計者は指摘を反映し、業務仕様の判断が必要な指摘はユーザーの確認対象に加える。要件の内容を補うか変える場合は、ユーザーが明確に伝えた内容を入れる場合を除き、設計者が確定せず、成果物の配置の「未確定の扱い」「変更案の書き方」に従って変更案として書き、ユーザーの確認対象に加える。上位の要件に及ぶ場合は、フローの適用単位の「見直し」に従う。修正後は、変更した範囲を再レビューする。

### 実装レビューの進め方

1. 対象の要件・設計・制約、実際の差分と関連する成果物、自己レビュー・検証結果、未確認事項を読む。気になる点は元の文書や関連する成果物をたどって確かめる。
2. 要件・設計に対して実装の抜けや余計な変更がないか、設計で決めた構成・流れ・データの扱いと一致しているか確認する。差分を確認する観点は分野の「レビューの観点」に従う。ある観点の結論で、別の観点で挙がった候補を打ち消さない。
3. 上位のレビューでは、下位の文書・成果・レビュー結果を参照し、下位同士のデータ・状態の扱いが整合し、上位の要件・設計が成立するか確認する。
4. 検証結果から、期待する動作を確かめられているか、確認漏れがないか確認する。
5. 承認済みの設計を変える修正は、セカンドオピニオンに基づくものも含め、変更案をユーザーに示し、再承認を得てから着手する。設計を変えない修正は合意した範囲内で進める。業務仕様の変更が必要な場合は、要件を判断する工程へ戻る。
6. 修正後は実装者が自己レビューと検証を行い、レビュワーが「前工程へ戻った場合とやり直す範囲」の基準で決めた範囲を再レビューする。

### 前工程へ戻った場合とやり直す範囲

- 前の工程へ戻った場合は、変更後の内容に基づいて、その工程から後続工程へ順に進め直す。承認済みの設計を変更する場合は、その設計についてユーザーの再承認を得てから「実装」に戻り、その実装を構成する下位の要件定義からテストまでを見直す。既に分かっている下位の承認済み設計の変更も、上位の変更案に含めて再承認を得る。再開後に承認された範囲を超える設計変更が必要になった場合は、その変更も実装前に再承認を得る。
- 各階層で影響を受ける工程と成果物をやり直し、影響がないと確認できる成果物と確認結果は引き継ぐ。下位の見直しを終えたら、変更した成果を組み合わせ、上位の実装レビュー・テストへ順に戻る。
- やり直す範囲は、変更行数ではなく、要件・設計の前提と各工程の成果・確認結果をどこまで引き継げるかで決める。メインエージェントが修正の原因と影響先を確認し、対象となる階層・下位の単位・工程と理由を短く示す。レビュワーもその範囲が妥当か確認する。

| 進め方 | 判断の目安 | やり直す範囲 |
| --- | --- | --- |
| 局所的な修正と再レビュー | 原因と影響する単位・工程を特定でき、それ以外の要件・設計・動作と確認結果が引き続き有効な場合。 | 当該階層と影響する下位の要件・設計を見直し、必要な実装・実装レビュー・テストをやり直す。上位では、変更箇所と利用先、関係するデータや動作を再確認する。 |
| 全体の見直しとレビュー工程のやり直し | 共通の要件・設計の前提が変わる、複数機能に影響する構造変更がある、同じ見落としが広く見つかるなど、対象全体の前提や確認結果の妥当性を見直す必要がある場合。影響を限定できない場合も含む。 | 対象となる単位を定め、変更した前提に関係する下位の開発フローを要件定義から見直す。必要な工程をやり直したうえで、その単位全体の実装レビュー・テストを行う。 |

## テスト・最終確認工程

- 目的: その階層の成果を分野の「検証手段」で確かめ、要件・設計と完了条件を満たすか確認する。上位では、下位の成果を組み合わせた業務の流れを確認する。
- 実装中の検証との関係: 実装中に確認した内容と結果を引き継ぎ、その階層の対象範囲全体について不足する確認を補う。対象の成果物・データ・環境・期待結果の変更で有効でなくなった結果は再確認する。
- AIの担当: 確認項目と期待結果を整理し、実行できるテストを行う。ユーザーが手動確認できる状態を整え、結果の取り込み、問題の調査・修正、再テスト範囲の整理を行う。本工程はテストセッションで行う。問題の調査と再テスト範囲の整理はテストセッションが、修正は原因のある工程のセッションが行う（役割「セッション」）。
- ユーザーの担当: 最終的な手動テストで、実際の業務や利用場面に照らして意図した結果になるかを確認し、受け入れを判断する。AIが用意した項目に加え、業務上気になる点も確認する。
- 完了条件: その階層の必要なテストが終わり、完了を妨げる問題が解消し、設計文書が最終の成果物と照合されている（設計工程の「実装後の設計整理」）。ユーザーの手動確認と受け入れは、業務上の成果を確認できる単位で行い、その単位の最終的な完了に含める。それより下位の単位は、テスト工程のAIの確認まで終えれば上位へ渡してよく、ユーザーの手動確認と受け入れは上位に含める。未実施や未解決の内容は明示し、確認済みとして扱わない。
- 関連する単位の受け入れ: 「完了条件」の受け入れの単位の例外として、複数の単位にまたがる改修の関連する単位（成果物の配置の「複数の単位にまたがる改修」）は、テスト工程のAIの確認まで終えれば中心の単位へ渡してよく、ユーザーの手動確認と受け入れは、中心の単位と同じ受け入れに含める。本工程では、関連する単位を、中心の単位を上位とする「受け入れを上位に含める下位の単位」と同じ扱いとする。
- 残すもの: 確認項目と期待する結果を単位の文書のテストの節に置き、未確認・問題ありの状態だけを付ける。AIの確認を終えてユーザーの手動確認を待つ間は、テストの節の先頭に「ユーザー受け入れ待ち」と記し、受け入れ後に削除する。受け入れを上位に含める下位の単位ではこの記載を置かず、上位の受け入れ後に、下位の未確認・問題ありの状態も上位の結果に合わせて更新する。問題を修正した項目は未確認に戻し、再確認後に空欄にする。未確認・問題ありの項目と「ユーザー受け入れ待ち」の記載がない状態を、その単位で必要な確認と受け入れが済んだ記録とする。受け入れ後は項目だけを残し、次回の変更時の回帰確認の元にする。
- 受け入れ済みの単位への変更: 改修に当たらない変更も含め、変更に合わせて確認項目を追加・修正し、既存の確認項目のうち変更の影響を受けるものとともに未確認にする。既存の確認項目を削除する場合は、手動テストへ渡すときに理由をユーザーに示す。下位の単位の変更が上位の確認項目に影響する場合は、上位のテストの節でも未確認にする。単位の文書がない場合は、成果物の配置の「改修に当たらない変更」に従い、確認項目と結果をユーザーへの報告で示す。

### テストの進め方

1. 設計工程で合意したテスト観点を出発点に、要件・設計と維持すべき既存動作から、入力・操作・期待する結果を整理する。分野の「検証手段」に挙げる確認対象と、実装で分かった条件を確認対象にする。
2. 上位では、下位同士のデータや状態の受け渡し、操作や処理をまたぐ動作、既存機能への影響を確認する。下位のテスト結果を参照し、組み合わせて初めて確かめられる動作をテストする。
3. 手動テストへ渡す前に、必要なレビュー修正と、分野の「検証手段」に挙げる実行できる確認を済ませる。失敗があれば原因を確認し、対象範囲の問題を修正・再確認する。実行できない確認は理由と影響を示す。
4. AIが手動テストの対象の版を分野の「版の識別」に従って特定し、必要な準備、操作、期待する結果を短くまとめ、ユーザーが実施する。結果は確認項目ごとに問題なし・問題あり・未確認で受け取り、項目外で気づいた点も受け取る。未確認の範囲を明確にする。
5. 問題が見つかった場合は、再現条件と期待結果との差を確認し、原因のある工程へ戻る。修正と再テストの範囲は、「前工程へ戻った場合とやり直す範囲」に従う。承認済みの設計を変更する場合は、実装へ反映する前にユーザーの再承認を得る。

## 調査手順

- 目的: 各工程の判断に必要な事実を、推測ではなく資料・成果物で確かめ、確認済みの事実と推定・未確認事項を区別して工程へ渡す。
- 対象: 単位の文書と上位の文書、プロジェクトの説明書・規約、分野の「調査の対象」に挙げる対象、変更履歴、外部仕様の公式資料。
- 進め方: 何を判断するための調査かを決め、必要な事実に絞る。上位の文書と既存の説明書から読み、次に成果物と履歴で確かめ、外部資料は公式のものを優先する。読んで分かった事実と、そこからの推定を分けて記録し、事実には出典（ファイルパスと行、コミット、URL）を添える。既知の名前や仕様でも、現行の一次資料を開いてから判断する。
- 報告の形: 結論、根拠の参照先、確認した資料の一覧、未確認事項と確認できない理由、確認しなかった範囲とその理由、判断に影響する前提を示す。工程の文書に残すのは、要件・設計・テストの判断に使った事実と参照先に限り、調査の経緯は残さない。
- 委譲: サブエージェントの利用条件は `~/.claude/CLAUDE.md` のサブエージェントの利用方針に従う。委譲するときは、対象の資料を先に、判断に必要な問い、対象範囲、報告の形を後に置いて渡す。分野の単位では、分野の「調査の対象」も依頼に書く。モデルとエフォートは「モデル」に従う。
- モデル: 調査は、メインエージェントのモデルにかかわらず中位の段のモデルで行う。モデルとエフォートは調査用のエージェント定義で定める。メインエージェントは `~/.claude/CLAUDE.md` の方針どおり、重要な根拠の原資料を確認する。
- 終える条件: 最初に見つかった資料で止めず、問いに関係する対象（上位の文書、利用先、既存の説明書）を読み終え、判断に必要な事実が根拠付きで揃ったか、確認できないと分かった時点で終える。確認できない事項は未確認として工程の判断へ渡し、推定で埋めない。

## skillへの反映

- 本文書と分野の文書が承認済みの原本で、skillはその反映先とする。変更は原本で案を作り、「未確定の扱い」に従って承認を得てから、対応するskillに反映する。skillだけを直接変更しない。
- 原本とskillは同じコミットで更新し、対応する版を履歴でたどれるようにする。skillの末尾に元文書のパスを記す。
- skillには、原本の該当節の本文に加えて、読む時期、他のskillへの参照、成果の要約など skill 間の導線だけを置く。導線は原本の規則を追加・変更しない範囲に限り、規則を含む場合は原本に先に書く。
- skillは同じリポジトリの `skills/` に置き、`~/.claude/CLAUDE.md` に目次を置く。リポジトリは `~/.claude` に取り込む。
- skillの名前は、入口を `dev-flow`、それ以外を `dev-flow-` で始まる名前とし、原本から作るskillを他のskillと区別する。分野のskillは `dev-flow-<分野>` とする。
- 各skillの本文は、コンパクション後に再注入される上限（1本 5,000 トークン）以内に収め、重要な指示を先頭に置く。トークン数は測れていないため、1字1トークンの見積りで文字数を目安にし、実際のトークン数は、skillを読み込んだセッションの `/context` の差分で反映時に確かめる。`/context` の出力は次の呼び出しで入力に入り、Messages を約 7,000 トークン増やすため、`/context` の差分で測るときは、skill を呼ぶ前後の差分から、短いメッセージを挟んだ `/context` の差分（出力 1 回分）と前の返答の分を引く。`/context` の Skills の欄は skill の一覧の分で、読み込んだ本文は Messages に数えられる。`/context` を使えない場合は、skillを1本ずつSkillツールで読み込み、セッションの記録に残るAPI呼び出しごとのusage（input・cache_creation・cache_readの合計）の差分から、前の呼び出しの出力トークンと、何もしない呼び出しの差分を引いて測る。超えたskillがあれば、分け方を設計で見直して再承認を得る。
- 「既存の単位を改修する場合」は入口と別のskill（dev-flow-revision）にし、既存の単位への変更を受けたとき（改修に当たるかの判定を含む）と、新しい単位で「進行中の変更」の節に書く内容があるときに読む。入口を上限に収めるためで、それ以外の新しい単位では読まない。
- 役割の「セッション」は入口と別のskill（dev-flow-session）にし、どのセッションでも入口の次に読む。入口を上限に収めるためで、原本では役割の項のまま置く。どのセッションでも読むskillが1本増え、入口から読まずに工程のskillへ進むとセッションの規則を読み落としうる欠点は、工程のskillとdev-flow-revisionの冒頭で先に読むよう導いて抑える。
- 入口のdescriptionと `~/.claude/CLAUDE.md` の導線は、開発以外の成果物（文書など）の単位の作成・改修も対象に含め、成果物が残り、要件の確認や承認が要る作業に適用し、一度の回答や小さな修正には適用しない、と書く。
- 原本の節とskillの対応は次のとおり。

| 原本の節 | skill |
| --- | --- |
| 本文書の役割（「セッション」を除く）、フローの適用単位、分野、成果物の配置（「既存の単位を改修する場合」を除く） | dev-flow（テンプレートは `assets/unit.md`） |
| 本文書の役割の「セッション」 | dev-flow-session |
| 本文書の既存の単位を改修する場合 | dev-flow-revision |
| 本文書の要件定義工程 | dev-flow-requirements |
| 本文書の設計工程 | dev-flow-design |
| 本文書の実装工程 | dev-flow-implementation |
| 本文書のレビュー工程（「前工程へ戻った場合とやり直す範囲」を含む） | dev-flow-review |
| 本文書のテスト・最終確認工程 | dev-flow-test |
| 本文書の調査手順 | dev-flow-research |
| 分野の文書の全節（「要件」を除く） | dev-flow-<分野>（開発分野は dev-flow-code） |

## 未実施事項

- 実作業での確認: 採用したフローを実作業で品質、手戻り、確認負担の面から確かめ、修正する。特に、テストやユーザーの指摘から前工程へ戻るときのレビュワーの起動、承認済みの設計の小さな変更が頻発する場合の再承認の負担、要件定義・設計工程に番号付きの進め方が要るか、「大規模で複雑な1機能を扱う場合」を工程別に分けるかを確かめる。
- 要件の抜けへの対策での確認: 「抜けの確認」の事項に過不足がないか、当たるものがない事項をユーザーへ伝える負担、要件で決める事項と設計で決める詳細の線引き、やり取りの文面を渡せる範囲、設計レビューでの要件への指摘が実際の抜けを捉えるか、ユーザーの確認対象と再レビューを増やしすぎないかを、実作業で確かめる。
- 実装前の読み方での確認: 文書が大きい単位への小さな変更や、コードを変える単位が多い変更で全体を読む負担、上位の文書を読む範囲の過不足、まとまりごとの読み直しと会話の履歴が要約された後の読み直しの負担を、実作業で確かめる。
- 改修での確認: 改修に当たるかどうかの線引き、「進行中の変更」の節・根拠の出典・既知の問題を書く負担、変更点の要約と本文の食い違い、改修が並行する場合の進め方と受け入れ、文書がまだない既存の単位で未記載の範囲が残り続けないか、テンプレートの形でない既存の文書の扱いを、実作業で確かめる。
- 複数の単位にまたがる改修での確認: 中心の単位を決める基準で置き場が決まるか、関連する単位の受け入れを中心の単位に含める進め方、中心の単位が一つに決まらない場合の完了条件の確認、改修の途中で改修として扱う単位が増減する場合の扱いを、実作業で確かめる。
- コメントの方針での確認: コードから読み取れない前提や採らなかった理由の書きすぎ、設計の節との重複、参照先の示し方、レビューや後の変更でより単純な書き方への見直しが実際に減るかを、実作業で確かめる。
- 分野を分けた構成での確認: 分野の skill がない単位で AI がその場で挙げる確認事項の過不足、分野の skill と dev-flow-revision と dev-flow-session を読む時期の過不足、別のセッションで再開するときとコンパクション後に skill を読み直す規則が要るかを、実作業で確かめる。
- 文書作成の分野: 骨格だけで文書の単位を進めた経験（効いた確認事項、見落とし、照合に使った手段）を材料に、分野の文書と skill を追加する。
- 進行中の変更の読者分けでの確認: 概要の文数の目安、承認の対象と管理の線引き、ユーザーが管理を読まずに承認できるか、加える改修案の書き方を、実作業で確かめる。
- セッション分離での確認: 親セッションの文脈の大きさ、fork で起こした設計セッションの文脈の大きさ、承認と受け入れをその工程のセッションで行う手間、テストで見つかった問題を原因の工程のセッションへ戻す流れ、CLI だけで使う場合の進め方を、実作業で確かめる。
- skill の合計サイズの見直し: 1 セッションで読む skill の本文の合計が、コンパクション後の再注入の合計上限 25,000 トークンに近いか超える（反映時の中位の段のモデルの実測では、開発分野の改修の実装セッションが関連の導線どおりにすべて読むと約 27,000 を超える）。実作業で実測し、条件に当たるときだけ読む節（dev-flow-code の「GUI設計」「大規模で複雑な1機能を扱う場合」、dev-flow-revision の「複数の単位にまたがる改修」）を補助ファイルに出すことと、利用者向けの操作手順（fork の CLI コマンド、親子の仕組みの有無による起こし方）を README へ移すことを、受け入れ後の別の改修として検討する。
