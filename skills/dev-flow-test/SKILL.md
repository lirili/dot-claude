# テスト・最終確認工程

dev-flowが定める工程の一つ。役割、適用単位、分野、成果物の配置はdev-flowに従い、未読ならdev-flowとdev-flow-sessionを先に読む。本文の分野の「節の名前」は単位の分野のskillの同名の節を指し、分野のskillがない単位ではdev-flowの「分野の skill がない場合」に従う。成果は単位の文書（dev-flowの `assets/unit.md`）のテストの節に置く確認項目・期待する結果・状態と、ユーザーの受け入れ。
- 目的: その階層の成果を分野の「検証手段」で確かめ、要件・設計と完了条件を満たすか確認する。上位では、下位の成果を組み合わせた業務の流れを確認する。
- 実装中の検証との関係: 実装中に確認した内容と結果を引き継ぎ、その階層の対象範囲全体について不足する確認を補う。対象の成果物・データ・環境・期待結果の変更で有効でなくなった結果は再確認する。
- AIの担当: 確認項目と期待結果を整理し、実行できるテストを行う。ユーザーが手動確認できる状態を整え、結果の取り込み、問題の調査・修正、再テスト範囲の整理を行う。本工程はテストセッションで行う。問題の調査と再テスト範囲の整理はテストセッションが、修正は原因のある工程のセッションが行う（役割「セッション」）。
- ユーザーの担当: 最終的な手動テストで、実際の業務や利用場面に照らして意図した結果になるかを確認し、受け入れを判断する。AIが用意した項目に加え、業務上気になる点も確認する。
- 完了条件: その階層の必要なテストが終わり、完了を妨げる問題が解消し、設計文書が最終の成果物と照合されている（設計工程の「実装後の設計整理」）。ユーザーの手動確認と受け入れは、業務上の成果を確認できる単位で行い、その単位の最終的な完了に含める。それより下位の単位は、テスト工程のAIの確認まで終えれば上位へ渡してよく、ユーザーの手動確認と受け入れは上位に含める。未実施や未解決の内容は明示し、確認済みとして扱わない。
- 関連する単位の受け入れ: 「完了条件」の受け入れの単位の例外として、複数の単位にまたがる改修の関連する単位（成果物の配置の「複数の単位にまたがる改修」）は、テスト工程のAIの確認まで終えれば中心の単位へ渡してよく、ユーザーの手動確認と受け入れは、中心の単位と同じ受け入れに含める。本工程では、関連する単位を、中心の単位を上位とする「受け入れを上位に含める下位の単位」と同じ扱いとする。
- 残すもの: 確認項目と期待する結果を単位の文書のテストの節に置き、未確認・問題ありの状態だけを付ける。AIの確認を終えてユーザーの手動確認を待つ間は、テストの節の先頭に「ユーザー受け入れ待ち」と記し、受け入れ後に削除する。受け入れを上位に含める下位の単位ではこの記載を置かず、上位の受け入れ後に、下位の未確認・問題ありの状態も上位の結果に合わせて更新する。問題を修正した項目は未確認に戻し、再確認後に空欄にする。未確認・問題ありの項目と「ユーザー受け入れ待ち」の記載がない状態を、その単位で必要な確認と受け入れが済んだ記録とする。受け入れ後は項目だけを残し、次回の変更時の回帰確認の元にする。
- 受け入れ済みの単位への変更: 改修に当たらない変更も含め、変更に合わせて確認項目を追加・修正し、既存の確認項目のうち変更の影響を受けるものとともに未確認にする。既存の確認項目を削除する場合は、手動テストへ渡すときに理由をユーザーに示す。下位の単位の変更が上位の確認項目に影響する場合は、上位のテストの節でも未確認にする。単位の文書がない場合は、成果物の配置の「改修に当たらない変更」に従い、確認項目と結果をユーザーへの報告で示す。

## テストの進め方

1. 設計工程で合意したテスト観点を出発点に、要件・設計と維持すべき既存動作から、入力・操作・期待する結果を整理する。分野の「検証手段」に挙げる確認対象と、実装で分かった条件を確認対象にする。
2. 上位では、下位同士のデータや状態の受け渡し、操作や処理をまたぐ動作、既存機能への影響を確認する。下位のテスト結果を参照し、組み合わせて初めて確かめられる動作をテストする。
3. 手動テストへ渡す前に、必要なレビュー修正と、分野の「検証手段」に挙げる実行できる確認を済ませる。失敗があれば原因を確認し、対象範囲の問題を修正・再確認する。実行できない確認は理由と影響を示す。
4. AIが手動テストの対象の版を分野の「版の識別」に従って特定し、必要な準備、操作、期待する結果を短くまとめ、ユーザーが実施する。結果は確認項目ごとに問題なし・問題あり・未確認で受け取り、項目外で気づいた点も受け取る。未確認の範囲を明確にする。
5. 問題が見つかった場合は、再現条件と期待結果との差を確認し、原因のある工程へ戻る。修正と再テストの範囲は、「前工程へ戻った場合とやり直す範囲」に従う。承認済みの設計を変更する場合は、実装へ反映する前にユーザーの再承認を得る。

## 関連

- 事実の調査はdev-flow-researchに従う。
- 問題が見つかって前の工程へ戻る場合、やり直す範囲はdev-flow-reviewの「前工程へ戻った場合とやり直す範囲」、承認済みの設計の変更はdev-flow-designの「承認後の変更」に従う。
- 受け入れ後の「進行中の変更」の節の削除と、照合の範囲は、dev-flow-revisionの「既存の単位を改修する場合」に従う。残す問題の書き方はdev-flow-designの「既知の問題」に従う。
- 完了条件を満たしたら、この単位の成果を上位の「実装」の成果として、dev-flowの「フローの適用単位」に従い上位の実装レビュー・テストへ進む。関連する単位では、「関連する単位の受け入れ」に従い、中心の単位の実装レビュー・テストへ進む。
