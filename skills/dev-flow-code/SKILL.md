# 開発フロー（開発分野）

dev-flowの「分野の決め方」で開発分野とした単位で、各工程のskillが分野の「節の名前」の形で参照する内容を定める。工程の順序と手順、役割、配置の原則はdev-flowと各工程のskillに従う。本文の「dev-flow.md の〜工程」はその工程のskillを、「dev-flow.md の『成果物の配置』」はdev-flowの節を指す。

## 単位と配置

- 単位の例: システム全体、サービス、機能、画面、コード内の処理。文書を持つ単位の例はシステム・機能・画面、文書を持たない単位の例はコード内の処理。
- 配置の例: システム全体は `docs/README.md`、機能は `docs/<機能>.md`、下位の単位があれば `docs/<機能>/<画面>.md` のように、階層に合わせて配置する。
- 下位の文書の例: 上位の文書の「実装」から参照する下位の文書は、その実現を担うサービス・機能・画面。

## 調査の対象

- 対象と周辺のコード（呼び出し元・利用先・データの定義）、ライブラリの公式資料、必要な場合は実行結果。

## 要件の確認事項

- 失敗・取消・入力不備・同時操作のときに期待する結果。
- 利用者や権限による違い。
- 既存の機能・既存のデータ・外部との受け渡しのうち維持するものと変えるもの。
- 性能・データ量・セキュリティ・運用の条件。

## 設計の確認対象

- 確認対象: GUI設計、操作・処理の流れ、データの構造と管理ルール、入出力と重要な例外時の扱い。
- 設計の階層: 全体設計ではシステム構成と責務、画面構成・配置・遷移の方針、利用できる共通部品・モジュールの用途と利用条件を示す。機能設計では全体設計を参照し、対象機能でどこに何をどう使うかを具体化する。既存の全体設計がある場合は利用し、今回の判断に必要な不足を補う。
- データ設計: 変更に関係する範囲で、扱うデータの項目・意味・関係・制約、取得元と保存先、更新・削除・受け渡しのルールを示す。既存データを変更する場合は互換性や移行の扱いも示す。型・精度などの詳細は、業務上の正しさやデータの整合性を判断するために必要な範囲で具体化する。
- 具体化の範囲: 個々のクラス・メソッドは、dev-flow.md の設計工程の「残すもの」と同じく、重要な境界・外部との契約・要件上の制約を決めるために必要な範囲だけ具体化する。
- 設計レビューでの確認: 共通部品の利用条件と整合するか確認する。

### GUI設計

- 画面構成と配置: 全体設計の方針を参照し、対象画面・ダイアログの役割、画面内の配置、遷移、呼び出し関係を示す。
- 画面とデータの対応: 表示・入力項目がどのデータに対応するか、読込・編集・確定時にどこへいつ反映されるかを示す。データ自体の定義・制約はデータ設計を参照する。
- 入力条件と状態: 必須・任意、初期値、入力可否、参照専用など、対象画面で必要な条件と状態を示す。状態や他項目によって条件が変わる場合は、その条件と確認時期も示す。共通の入力規則は参照し、画面固有の条件を具体化する。
- 操作と状態変化: 項目の選択、フォーカスの取得・喪失、編集の開始・終了に応じた動作、入力値の確定と画面全体の保存・取消の条件を必要な範囲で示す。入力検証・エラー表示・他項目への反映のタイミングと、検証が成立しない場合の扱いを明確にする。選択・フォーカス・編集・入力値の確定・保存を区別する。
- 共通部品・モジュールの利用: カスタムコントロールを含む既存の画面部品・共通モジュールの仕様と利用条件を確認し、対象機能の動作に関係する使用機能・設定・データの受け渡し・機能側が担当する処理を定める。共通側が提供する挙動は参照し、機能固有の使い方と差分を記述する。内部の実装手順やイベントハンドラーまで固定するのは、判断に必要な場合に限る。

### 大規模で複雑な1機能を扱う場合

- 全体像: 機能全体の目的、主要な業務の流れ、ダイアログの役割と遷移、共有するデータ・状態、確定・取消の意味、全体の完了条件を概略で押さえる。既存コードで確認した現状と、要望・推定・未確認事項を区別する。
- 要件の具体化: AIが会話・既存資料・コードから短い案を作り、今進める範囲の判断に必要な部分だけ詳しくする。ユーザーに全要件の一括記述を求めない。合意した目的・制約・判断基準と承認済みの設計の範囲内の選択はAIが行い、業務上の結果や重要なデータの扱いを変える選択はユーザーに確認する。
- 作業単位と順序: 重要な技術的仮説や一連の業務動作を確認できる単位で進める。複数ダイアログをまたぐ場合も、強く依存する処理は一緒に扱う。後続へ広く影響する不確実性を早めに検証し、その結果を踏まえて範囲を広げる。作業分割を、そのままクラス分割や並列実装の理由にしない。
- 全体整合: メインエージェントが共有ルールと依存関係を把握し、実装・レビュー・統合を担当する。共有データや画面間のルールを変更した場合は、影響する業務の流れを確認する。各部分の検証に加えて、統合の節目と最後に必要な全体動作を確認する。
- 文書構成: 全体概要と共通ルールを基準に、業務のまとまりや画面群に固有の判断・例外を必要な範囲で詳しくする。全体概要から詳細をたどれる形にし、同じ仕様は重複記載しない。文書を分けるかどうかは dev-flow.md の「成果物の配置」の分割の基準に従う。
- ユーザーへの提示: 今回判断する内容と、その理解に必要な前提・影響を短く示す。小さな作業単位ごとのユーザーの承認、同じ文書の全文再確認、全体テストの一律反復を既定にせず、重要な判断や共有ルールへの影響に応じて選ぶ。

## 作成時の方針

- 実装前に読む対象: 変更する処理・呼び出し元・受け渡すデータ。
- 流れの整理: 処理の順序・主な分岐・データの変化を、ソース内のコメントで整理する。見直しによる修正はコメントとコードに反映する。
- 既存コードの再利用、追記の配置、責務の整理、共通化の一般則は `~/.claude/CLAUDE.md` の実行・運用ルールに従う。以下は実装工程での具体化。
- 今回必要な処理を書く。将来使うかもしれないクラス・メソッド・設定・抽象化・依存関係は増やさない。
- 要件・設計に挙げていない例外的な条件（環境に依存する制限、まれな入力、要件の確認事項で対象としなかった入力不備など）への対応は実装しない。気づいた条件は、該当箇所のコメントに注記するか、未確定事項としてユーザーに示す。動作を保証できない環境依存の条件は、注記で足りる。
- 既存実装がある場合は、実装前に類似する処理を調べ、構成・書き方・実装方法を理解したうえで既存のやり方に合わせる。
- 改行・インデントは既存の規約・フォーマッター設定に従い、規定がない部分は周囲のコードに合わせる。処理の階層や式・引数のまとまりが分かる位置で改行し、同じ構造には同じ改行・インデントの規則を適用する。行長制限に対応する場合もその規則に従い、長さの感覚だけで任意の位置に改行を入れない。
- 分割・共通化は実装前に決め切る必要はない。一つのまとまりとして実装した処理も、役割を分ける利点や同じルールをまとめる必要性が分かった時点で、分割・共通化する。
- メソッドやクラスを分けるときは、分けた先の役割が名前から分かり、呼び出す側の流れを追いやすくなるか確認する。別々に変更・確認する必要がある処理は分ける。行数の増加や呼び出し回数は見直しのきっかけにとどめて分ける基準にはせず、読むための往復だけが増える分け方は避ける。
- 今回作った試作コードや暫定処理は、採用した実装に必要なものだけ残す。変更箇所に残った不要な記述や、不自然な空白・空行も整理する。
- コメントは実装に合わせて更新し、完成後は処理の意図や流れの理解に役立つものを残す。コードから読み取れない前提や制約（外部仕様、回避策、順序の条件など）と、より単純に見える書き方を採らなかった理由は、該当箇所のコメントに残す。設計の節に書いた判断に依る場合は、理由を複写せず参照先を示す。

## レビューの観点

- 主要な操作・処理の流れを追い、入力条件、例外時の扱い、データの更新、画面やサービス間の受け渡し、既存動作への影響を確認する。削除・置換した処理が守っていた条件の移り先、変更した関数の呼び出し元と呼び出し先、例外・境界・並行実行の経路は個別に見る。
- 変更箇所と周辺コードを読み、処理の流れ・役割・修正箇所を把握しやすいか確認する。コメントが意図や流れの理解に役立ち、実装と一致しているか、改行・インデントが既存の規則に沿っているか確認する。不要なコード・試作の残骸・不自然な空白や空行など、読む際のノイズも確認する。
- 実装が入り組んでいる場合は、要件との対応と採用理由を読み、要件自体に必要な複雑さか、実装方法で生じた複雑さかを確かめる。業務ルール・例外・独立して変わる部分を正確に表し、それぞれの変更箇所を追えるか確認する。
- 実装方法に改善の余地があれば、同じ要件・既存仕様・制約を満たす代案を検討し、保守上の利点・変更範囲・影響・欠点を短く示す。現在の構成が妥当なら必要な複雑さを維持し、業務上の意味や区別を変える単純化は行わない。採用理由が現在の条件でも成立していれば、新たな根拠なしに同じ見直しを繰り返さない。

## 検証手段

- テストの対応: 部品を個別に確認する単体テストから、組み合わせた際の受け渡しや連携を確認する結合テストへ進み、最上位ではシステム全体の要件を確認するシステムテストを行う、という考え方に近い。テストの分類は確認対象と目的で決まり、文書の階層の段数とは一対一に対応させない。
- 実装中の検証: プロジェクトの説明書や既存の実行設定から、ビルド・静的解析・自動テストの実行方法を調べる。指定された確認と、今回の変更やその利用先を確かめるために必要な既存の確認を実行する。既存のテストで確認できない動作は、実行できる範囲で対象機能を動かして確かめる。
- テストの確認対象: 主要な業務の流れに加え、変更に関係する境界条件、入力不備、失敗・取消時の扱い。
- 手動テストへ渡す前に済ませる確認: 実行可能な既存のビルド・静的解析・自動テスト。
- 自動テストを追加・変更する場合（dev-flow.md の実装工程「実装の進め方」の 1 で確認方法を決めるときに従う）:
  - 既存のソース内に自動テストのコードがないテスト未導入プロジェクトでは、ユーザーの明示依頼なくテストコードを新規追加しない。既存のビルド・静的解析・動作確認で検証する。
  - 検出したい不具合と、要件・設計から判断した期待結果を説明できるテストに絞る。入力に対する結果やデータの変化を確認し、実装内部の手順を写すだけのテストを増やさない。値や文言の完全一致は、それ自体が要件である場合に確認する。
  - 不具合を検出する価値と保守の手間を比較する。業務仕様が変わらなくても実装の書き換えで壊れるテストは、確認対象や方法を見直す。

## 版の識別

- 変更単位ごとに、差分の自己レビューと必要な検証・修正を終えてコミットする。
- 手動テストの対象の版は、コミットIDまたはビルドの識別子で特定する。
