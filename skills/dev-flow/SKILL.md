# 開発フロー

要件定義→設計→設計レビュー→実装→実装レビュー→テストを、目的と完了条件を説明できる単位に入れ子で適用する。このskillは入口として、工程の順序と読むskill、役割、適用単位、分野、成果物の置き場所を定める。各工程の進め方は工程ごとのskillを読む。

## 工程と読むskill

依頼を受けたら、対象の単位と階層を決め、成果物の配置の「単位と文書」の置き場にある既存の文書を確認し、単位の分野を「分野」で決めて、次の表に従ってskillを読む。改修に当たるかの基準になる「ユーザーの確認対象」はdev-flow-designにある。前の工程へ戻る場合のやり直す範囲は、dev-flow-reviewの「前工程へ戻った場合とやり直す範囲」に従う。

| 工程・規則 | skill | 読む時期 |
| --- | --- | --- |
| セッション | dev-flow-session | どのセッションでも本skillの次に。 |
| 分野 | 「分野」の一覧のskill | 分野の単位で、どのセッションでも本skillの次に。 |
| 改修 | dev-flow-revision | 既存の単位への変更を受けたとき（改修に当たるかの判定を含む）。新しい単位で「進行中の変更」の節に書く内容があるとき。 |
| 要件定義 | dev-flow-requirements | 依頼を受けたとき。上位の実装から下位の単位を始めるとき。 |
| 設計 | dev-flow-design | 要件定義の「次へ進む条件」を満たしたとき。承認済みの設計を変える必要が出たとき。 |
| 設計レビュー | dev-flow-review | 設計案を承認に出す前。承認済みの設計の変更案を再承認に出す前。 |
| 実装 | dev-flow-implementation | 設計の「次へ進む条件」を満たしたとき。 |
| 実装レビュー | dev-flow-review | 実装の「実装レビューへ進む条件」を満たしたとき。 |
| テスト | dev-flow-test | 実装レビューの「次へ進む条件」を満たしたとき。下位の成果を組み合わせて上位を確認するとき。 |
| 調査 | dev-flow-research | 各工程で、既存の文書・成果物・履歴・外部資料から事実を確かめるとき。 |

## 役割

- ユーザー: 要件・設計の判断と承認、受け入れを行う。
- メインエージェント: 業務仕様の解釈、設計判断、実装、統合、最終検証を担う。単に「AI」と書く場合と、設計工程の「設計者」、実装工程の「実装者」はメインエージェントを指す。`~/.claude/CLAUDE.md` の条件で実装を委譲した場合も、確認と統合はメインエージェントが行う。
- レビュワー: 設計者・実装者とは別のエージェント。要件・設計・制約と、設計案または実際の差分を渡され、独立に確認する。
- サブエージェント: 調査・レビューなどの委譲先。利用条件は `~/.claude/CLAUDE.md` のサブエージェントの利用方針に従う。
- セッション: dev-flow-sessionにある。
- レビュワーのモデル: レビューは、レビュー対象を作ったエージェントと同じモデルで、作った側以上のエフォートで行う。委譲には、呼び出したセッションのモデルを継承しエフォートを固定したレビュー用のエージェント定義を使い、新しいコンテキストで起動する。分野の単位では、その分野の skill を preload したレビュー用のエージェント定義を使う。分野の skill がない単位と、レビュー用の定義がない分野では汎用の定義を使い、後者では分野の skill を Skill ツールで読むよう依頼に書く（「分野」）。エフォートの値はエージェント定義（`~/.claude/agents/`）で定める。既定のサブエージェントのモデルを設定する項目（`CLAUDE_CODE_SUBAGENT_MODEL`）は使わない。

## フローの適用単位

- 基本: 目的と完了条件を説明できるまとまりに、要件定義→設計→設計レビュー→実装→実装レビュー→テストを入れ子に適用する。単位の例は分野の「単位と配置」に挙げる。各階層の要件定義・設計・設計レビュー・実装レビュー・テストは、その階層の対象全体について行う。固定の階層数を前提にせず、実際の責務・包含関係・利用関係に合わせて単位を選ぶ。
- 文書と工程の対応: 上位の文書では「実装」から、その実現を担う下位の文書を参照する（例は分野の「単位と配置」）。下位の文書には、その対象の要件定義→設計→設計レビュー→実装→実装レビュー→テストの流れをまとめる。この下位の開発フロー全体が、上位の「実装」に当たる。下位の「実装」も必要に応じて、さらに下位の文書と開発フローへ展開する。
- 上位から下位へ: 上位で目的・全体像・責務の境界・共有データや契約・制約・完了条件を押さえ、下位では担当範囲に必要な内容を具体化する。上位のすべての詳細を決め終えてから下位へ進む必要はなく、未確定の前提に依存する範囲を明確にして進める。
- 下位から上位へ: 上位で今回扱う範囲に必要な下位の開発フローがテストまで完了したら、その成果を組み合わせて上位の実装レビュー・テストを行う。上位の要件・設計と完了条件を満たせば、そこまでの成果がさらに上位の「実装」の成果となり、その上位の実装レビュー・テストへ進む。未対応・未確認の範囲も引き継ぎ、部分的な完了を対象全体の完了として扱わない。
- 見直し: 下位の調査・設計レビュー・実装・実装レビュー・テストで、合意した要件・設計を変える必要が判明した場合は、影響範囲を確認し、その要件・設計を管理する階層の判断へ戻る。影響する他の単位と共通ルールも見直す。
- 上位の不足: 下位の作業で、複数の単位に共通する構成・データ・ルールの判断が必要だと分かった場合は、それを管理する上位の文書を作るか既存の上位文書に補い、ユーザーの確認を得てから下位に戻る。上位全体を決め直すのではなく、今回の判断に必要な範囲に限る。
- 共通事項と個別事項: 共通の要件・設計・判断基準は上位を参照し、下位には固有の内容と差分を記述する。同じ工程を適用しても、各階層の文書と承認は、その階層で決めた固有の内容と差分に限り、上位で承認済みの内容を再確認しない。ユーザーへの確認は、各階層の固有の判断、業務上の成果を確認できる単位での受け入れ、承認済みの設計の変更に必要な範囲で行う。

## 分野

- 分野: 成果物の形によって確認観点と検証手段が変わるまとまりを分野と呼ぶ。分野に固有の内容は、分野ごとの文書（`docs/dev-flow-<分野>.md`）に、単位と配置、調査の対象、要件の確認事項、設計の確認対象、作成時の方針、レビューの観点、検証手段、版の識別の節で書く。各工程の記述は、分野固有の内容を「分野の『節の名前』」の形で参照する。
- 分野の決め方: 単位ごとに決める。単位の成果物に、実行・ビルド・テストで確かめるコード・スクリプト・設定が含まれるなら開発分野とする。ここでの「確かめる」は、成果物の正しさを実行・ビルド・自動テストの結果で判定することを指す。Claude Code の設定・skill・エージェント定義のように、読まれて指示として働き、読んで照合して正しさを判定する成果物は、開発分野に含めない。開発分野でない単位は分野の skill を読まず、骨格（本文書の各工程）だけで進める。
- 分野の skill: 分野の文書は 1 本の skill に反映し（「skillへの反映」）、どのセッションでも入口の次に読む。
- 工程の名前: 「実装」は、分野にかかわらず単位の成果物を作る工程を指す。工程の名前は分野で変えない。
- 分野の一覧:

| 分野 | 文書 | skill | レビュー用エージェント定義 |
| --- | --- | --- | --- |
| 開発 | `docs/dev-flow-code.md` | dev-flow-code | reviewer-code |

- 分野の skill がない場合: 各工程の記述が分野の節を参照する箇所では、AI が対象の成果物に合わせて該当する内容をその場で挙げる。要件定義・設計では、挙げた内容をユーザーの確認対象に含める。実装・レビュー・テストでは、挙げた内容を自己レビュー・検証の結果とともに示す。レビューの委譲には汎用のエージェント定義（reviewer）を使い、挙げた内容を渡す。
- 分野の追加: 分野の文書と skill を同じ節構成で作り、分野の一覧に加える。レビュー用のエージェント定義を作る場合は、既存の定義と同じ形で追加する。

## 成果物の配置

- 単位と文書: 単位ごとに1文書を、対象プロジェクトの `docs/` に置き、階層に合わせて配置する。プロジェクトのフォルダがない成果物では、成果物と同じ場所に置く。配置の例は分野の「単位と配置」に挙げる。文書を持つ単位は、独立した要件・設計・テストを持つ単位に限る。文書を持たない単位は、それを含む文書の設計と実装の節の中で扱い、工程は同じ順で適用するが文書一式は作らない。
- 文書の位置づけ: 単位の文書は、開発者がその単位の現在の仕様を知るための文書として、単位がある間は維持する。依頼や変更ごとに要件・設計の文書を作らない。
- 文書の構成: 節は要件、設計、実装、レビュー、テストとする。「進行中の変更」の節は、書く内容がある間だけ要件の節の前に置く。実装の節には下位の文書への参照を置き、下位を持たない場合は、その単位を実現する成果物の場所や主要な参照先を示す。レビューの節は、未解決の指摘がある間だけ置く。
- テンプレート: 単位の文書のテンプレートは `assets/unit.md`。
- 記述の範囲: 文書は現在の要件・設計・未実施事項だけを持つ。レビューの指摘やテストの結果は、未解決・未確認のものだけを該当する節に残し、解消したら削除する。経緯や作業ログは残さない。
- 重複を避ける書き方: 同じ説明を複数の箇所に繰り返さない。複数の箇所で使う用語は一度だけ定義して参照し、複数の条件が組み合わさる判定は表にまとめる。
- 根拠の出典: 判断に使った資料や成果物の参照先は、調査手順の「報告の形」に従って残す。承認するユーザー以外の人に確認した業務ルール・外部仕様のうち、成果物や他の文書から確かめ直せないものには、確認先を部署や役割で該当箇所に短く添え、個人名や確認までの経緯は書かない。
- 更新の仕方: 未確定の事項が確定したら、決定内容を本文の該当箇所に反映し、未確定としての記載を削除する。「決定済み」「反映済み」などの注記や決定までの経緯を追記せず、未確定の事項がなくなった欄や見出しも削除する。
- 未確定の扱い: 未確定の節や項目には「案（未確認）」のように印を付け、確定した内容と区別する。追記と見直しを重ねて項目内の記述を完成させ、ユーザーが確認して合意した時点で印を外す。印の付いた内容を、承認済みの要件・設計として扱わない。
- 分割の基準: 文書を分けるかどうかはサイズではなく、独立した要件・設計・テストを持つ単位かどうかで決める。
- 全体の目的と計画: プロジェクト全体の目的・範囲・制約・完了条件は最上位の文書の要件の節で、単位の分割は実装の節で、進める順序は「進行中の変更」の節の管理で扱う。憲章や計画の別の様式は、必要になった時点で検討する。

### 既存の単位を改修する場合

dev-flow-revisionにある。

## 元文書

- `~/.claude/docs/dev-flow.md` の「役割」（「セッション」を除く）「フローの適用単位」「分野」「成果物の配置」（「既存の単位を改修する場合」を除く）。本文の「skillへの反映」は元文書の節を指す。変更は元文書を先に更新し、承認を得てから本skillに反映する。
